## 2. geometry-g7 / sa7-01-03 — FIXED

**Rationale** (`S248-G7-sa7-01-03-lfnorm`, latest): (a) both concept figures teach only prisms though the
title promises pyramids, and the challenge (`ch1`) requires pyramid surface area without a pyramid/net
representation; (b) `c2` and the remedial concept overclaim "the same rule works for any prism" when the
guarantee is for right prisms only in this context. `reopenCondition` requires both fixes together.

**Built**: two new components in `figures.tsx`:
- `Sa7PyramidParts` → `"sa7-pyramid-parts"` — a dimension-free square-pyramid net (1 square base + 4
  triangular faces = 5 faces), bound to `k3` ("How many faces does a square pyramid have?"), which asks
  only about face count, not dimensions.
- `Sa7PyramidNetTotal` → `"sa7-pyramid-net-total"` — the same net shape, dimensioned to match `ch1`
  exactly: base edge 6, slant height 5, base area 36, four triangles of 15 (60 total), grand total 96 —
  the exact numbers `ch1`'s widget already asks for and grades.

Every existing `sa7-*` figure (`Sa7NetUnfold`, `Sa7TriangularPrismParts`, `Sa7LateralShortcut`, etc.) was
left untouched; both new functions are pure additions.

**Content fix (part b)**: in both `c2`'s `body`/`narration` and the remedial concept's `body`, changed
"The same rule works for any prism, whatever polygon its end happens to be." to "...any **right** prism,
...". The correct number (perimeter 12, length 10, lateral 120, total 132) and every evaluator/answer is
unchanged.

**Action-step invariant, verified by hand**: `sa7-01-03` has 8 main steps: `c1` (concept), `i1`
(interactive), `k1` (check), `c2` (concept), `k2` (check), `k3` (check), `ch1` (challenge), `r1` (recap).
Per `src/lib/pedagogy.ts`'s `ACTION_KINDS = {interactive, check, challenge}`, action steps are `i1, k1,
k2, k3, ch1` = 5 of 8 = **62.5%**, above the 60% floor. This was true before this session's edit too
(no step was added, removed, or had its `kind` changed — only `figure` keys and two sentences' wording
changed), so the invariant is unaffected by, and was already satisfied prior to, this edit. The task
brief's cited baseline ("only 56% ... fails") does not match a hand count of the lesson file as currently
authored on disk; reporting the actual computed number (62.5%) rather than silently accepting the
brief's figure. No interactive/check step needed to be added.

## 3. transformations-measurement / tm-03-02 — FIXED

**Rationale** (latest by `reviewedAt`: `S251-COARSE-BASIS-tm-03-02-lfnorm`, standards-locator rebasing of
the original `S246-TM-tm-03-02` assessment, content judgment unchanged): `c2`'s right-triangle example is
withheld at runtime because no figure renders a synchronized right-triangle representation for 90°, 35°,
and the inferred 55°; the fallback to prose at this "explicitly spatial" representation change is the
defect.

**Confirmed the withholding mechanism** (per the prior rejection note): `figureTextBindingKey("la-triangle-sum",
plain(c2.body))` hashes to `2ff13c9b`, present in `FIGURE_TEXT_MISMATCH_BLOCKLIST`, so `la-triangle-sum`
(a generic a/b/c triangle with no right-angle marking) was runtime-withheld for this step, and the
lesson fell back to prose-only.

**Built**: `TmRightTriangleAngleSum` → `"tm-right-triangle-90-35-55"` in `figures.tsx` — an actual
three-vertex right triangle (`<polygon>`), with a shape-based right-angle marker (a small unfilled
`<rect>`, not a colour cue) and text labels for 90°, 35°, and "55° (inferred)", plus a caption
"90° + 35° + 55° = 180°". This is the exact semantic figure the reopenCondition names: it is neither
`McMissingAngle` (a single-vertex angle split at one corner, not a three-vertex triangle — reusing it
would introduce a new representation mismatch) nor `LaTriangleSum` (generic, no right angle, no numbers).

**Bound**: `c2.figure` changed from `"la-triangle-sum"` to `"tm-right-triangle-90-35-55"`. `c2`'s
body/narration text is unchanged.

**Verified not gaming the gate**: a jsdom test (`miscFigures.s316.test.tsx`) computes
`figureTextBindingKey("tm-right-triangle-90-35-55", c2.body)` and asserts it is absent from
`FIGURE_TEXT_MISMATCH_BLOCKLIST`, and separately asserts `isFigureTextAligned(...)` is `true`. The fix
clears the WITHHELD state by rendering the actually-demanded visual, not by editing the lesson's numeric
example to produce a fresh, not-yet-blocklisted hash for the *old*, still-mismatched figure — the path
the prior rejection explicitly identified as gaming and refused to take.

## 4. bivariate-statistics / bv-05-03 — FAIL-CLOSED (unchanged)

**Latest rationale** (`S247-BV-bv-05-03-OLS-SUPERSESSION-lfnorm`): the earlier mathematical ESCALATE
(false least-squares result) is superseded — the lesson JSON already carries the corrected OLS math
(ŷ = 1.9x + 1.5; residuals −0.4, +0.7, −0.2, −0.1; SSE 0.70; shifting the intercept by +0.7 gives SSE
2.66), all matching the `i1`/`k1`/`k2` widgets and text on disk today. The lesson remains REVISE because
the **shared `scatterFit` widget** calls its graded quantity "miss"/reports an MSE value the learner text
never uses (learner text consistently says SSE 0.70), and its SVG/state accessibility description does
not expose residual magnitudes or the scored fit metric to nonvisual learners. `reopenCondition` demands
the shared `scatterFit` surface be relabeled consistently (MSE vs SSE) and its accessibility description
be expanded, plus new focused renderer/evaluator tests for keyboard, screen-reader-equivalent,
reduced-motion, and narrow-view behavior.

**Checked**: `grep -n "function ScatterFitW" src/components/widgets.tsx` → the entire readout (`mse`
computation, `aria-label` template, `title`, tick labels) is generated inside `ScatterFitW`
(`src/components/widgets.tsx`, ~line 9709), the one shared renderer used by every lesson with a
`scatterFit` widget — not a `figures.tsx` figure. `c1` (`bv-residuals-steer-the-line`) and `c2`
(`bv-least-squares`) already carry correctly-matched, already-registered `figures.tsx` figures; neither
is missing nor mismatched, so there is no figures.tsx gap to fill for this lesson.

**Decision**: fail-closed. The demanded fix is a shared interactive-widget renderer/accessibility change
plus new renderer tests in `src/components/widgets.tsx`, outside this task's `figures.tsx`-only scope
(house rules: "figures.tsx additions are additive only"; task scope explicitly names `figures.tsx`, not
`widgets.tsx`). No lesson JSON or `figures.tsx` edit was made for `bv-05-03`. Flagging for a worker with
`widgets.tsx` write access — per the task instruction, this fail-closed outcome is treated as success,
not as an incomplete batch.
