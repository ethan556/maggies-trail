# S330 Progression Packet G4 — LESSON_PROGRESSION_AND_DUPLICATION

Scope: queue workstream `LESSON_PROGRESSION_AND_DUPLICATION` (generated by
`scripts/audit/consolidate-pending-workload-s236.mjs`, lines ~358-393), the 12 lessons assigned to
packet G4 across two courses: `measure-money-time` (mmt) and `the-real-number-system` (rns).

**Method.** The detector was reproduced verbatim (lowercase, strip digits to `#`, collapse whitespace,
cluster by identical normalized `widget.prompt` template within one lesson) as a standalone script and
run against every lesson's live JSON, both to confirm the queue's flagged step IDs and to find each
flagged step's actual colliding sibling(s) — every one matched the assignment exactly. Every lesson was
then read in full, including surrounding concept cards, `body`, `explanationVariants`, and `hints`, to
judge whether the collision is defensible fluency/retrieval practice (KEEP) or a later step (usually the
challenge) posing the identical question job as an earlier step with no distinguishing content (REDESIGN).

Result: **8 lessons KEPT, 4 lessons REDESIGNED** (mmt-03-03: `i3`,`k3`,`ch1`; mmt-05-03: `k3`,`ch1`;
rns-03-01: `ch1`; rns-03-02: `ch1`).

All edits verified: `JSON.parse`, the real `LessonSchema.parse` + `WidgetSpec.parse` +
`widgetIntegrityErrors` + `lintLesson` (zero findings on all 4 edited files), the corpus-wide
solvability gate (`content.widgets.audit.test.ts`, no failures attributable to these 4 files — the 2
failures it reports, in `g4x-02-01` and `sy-01-01`, are pre-existing and outside this packet), the mmt
course test (`session268.measureMoneyTimeCourse.test.ts`, 2/2), the plotData corpus contract
(`content.plotData.s237.test.ts`, 30/30 — load-bearing for mmt-05-03's redesign), and the variant
resolver contract (`variants.resolver.test.ts`, plus a standalone `variantForStep` check for the two
repointed/deleted variant declarations in rns-03-01 and rns-03-02).

## mmt-03-01 — What Are Coins Worth?

Flagged: `k1`.
- `k1` collides with `i1`: both mcq "Which coin is worth # cents?" — `i1` (dime, 10¢) is the intro
  worked example right after concept `c1` introduces all four coin values; `k1` (quarter, 25¢) is the
  immediate first check, drilling a **different specific coin fact** with the same question frame. For
  an atomic vocabulary lesson (memorize four coin values), reusing the identical question frame per new
  fact is the ordinary way to check each one — not a redundant repeat of the same fact. `k2` (penny, "1
  cent" singular) tests the identical skill again but never collided at all, confirming the pattern is
  simply "one check per fact."

**Decision: KEPT — no edit.**

## mmt-03-03 — How Many Coins Make That?

Flagged: `i3`, `k3`, `ch1`.
- `i3` collides with `i2` ("How many quarters make # cents?"), `k3` collides with `k1` ("How many dimes
  make # cents?"), `ch1` collides with `i1` ("How many nickels make # cents?"). All three are the same
  defect: after concept `c3` introduces the "$1 = 100 cents" milestone, the lesson's back half revisits
  every coin at that milestone (`i3`=quarters→100¢, `k3`=dimes→100¢, `ch1`=nickels→100¢), but the
  **prompt text still said "100 cents"** instead of "one dollar" — colliding verbatim with each coin's
  earlier arbitrary-total item. Each step's own `body`/`explanationVariants` already said "dollar"
  (`ch1`'s second explanationVariant literally read "Twenty nickels make a dollar") — the widget prompt
  just never caught up.

**Decision: REDESIGNED** (all three). **Old job:** "How many {coin} make 100 cents?" (identical text to
the earlier arbitrary-total item, just reusing the number 100). **New job:** "How many {coin} make one
dollar?" — a real representation/transfer change (recognizing 100¢ = $1, which concept `c3` teaches but
no graded step previously tested), not a cosmetic reword. Underlying `targetCents`/`tray`/`answer` are
unchanged; math re-verified: 100÷25=4 quarters, 100÷10=10 dimes, 100÷5=20 nickels. No `variant` field
existed on `i3`; `k3`/`ch1` keep `widget.type: "moneyBoard"` so their existing
`g2-measure-money-time`/`MmtCoinReverseMoneyBoard` declarations still resolve to the same surface (the
generator's own prompt wording already differs from the authored text by established precedent in this
lesson, so this was not a new mismatch).

## mmt-05-03 — Reading a Line Plot and Comparing Data

Flagged: `k3`, `ch1`.
- `k3` collides with `i1`: both "A line plot shows # x's above the number # and # x above the number #.
  How many data points are at #?" — the match is a coincidence of grammar (both happen to have a
  second-stack count of exactly 1, forcing singular "x" instead of "x's"), but the underlying job really
  was identical: a plain 2-stack count-read with no new misconception.
- `ch1` collides with `k2`: both "Monday has # votes and Tuesday has # votes. How many more votes on
  Tuesday?" — a textbook check-then-challenge duplicate with no distinguishing content.

**Decision: REDESIGNED** (both).
- `k3` **old job:** read the count at a named value from a 2-stack plot (same job as `i1`/`k1`). **New
  job:** a 4-stack plot (values 3, 5, 7, 9; counts 2, 6, 1, 4), asked "How many data points are at 7?"
  (=1) while the *tallest* stack (6, at value 5) sits elsewhere — a "don't default to the tallest stack"
  misconception not tested by `i1`/`k1`/`i3`. Kept the plotData field and the recognized "N x's above
  the number M" sentence shape so the S237 plotData corpus contract still holds (re-run,
  30/30 passing) — confirmed by hand: index of 7 in [3,5,7,9] → counts[2] = 1, matching the authored
  answer.
- `ch1` **old job:** bare numeric subtraction fact, identical shape to `k2`. **New job:** the same
  `lengthCompare` "difference" widget `i2` already uses in this lesson (visual overhang-counting instead
  of typed subtraction — a genuine representation change), with Monday=9 > Tuesday=8, deliberately
  inverting the "Tuesday is always bigger" pattern every earlier item (`i2`, `k2`, the old `ch1`)
  established, targeting a new "the first-named quantity can still be the larger one" misconception.
  Verified 9−8=1, `diffMax`=9=longer bar, `answerId` names the longer bar per the schema's own integrity
  rule. Deleted the now-mismatched `numeric`-producing variant tag (`MmtGraphCompareNumeric`) rather than
  touch the shared `g2Variants.ts` — no sibling `lengthCompare` form exists in that generator family.

## rns-01-01 — What Makes a Number Rational

Flagged: `ch1`.
- `ch1` collides with `k4`: both "#/# as a decimal is:" (choice among four decimal representations).
  `k4` classifies 9/20 (terminates cleanly in 2 steps); `ch1` classifies 5/11 (a 2-digit repeating block,
  requiring two full remainder cycles to recognize — the hardest instance in the family, and `ch1`'s own
  distractor "0.4, repeating" tests a block-boundary misconception `k4`'s terminating fraction can't even
  present). Considered redesigning to an inverse ("given the decimal, name the fraction") or a
  predict-without-dividing shortcut, but both belong to explicitly *later* lessons per this lesson's own
  teaser ("Next: predicting which fractions terminate and repeat — before you ever divide") and
  rns-01-03's dedicated `repeatToFraction` task — using either here would preempt reserved content. The
  engine's `decimalSelect` task also only supports a binary terminates/repeats `classificationTarget`,
  so a richer "which has the longest block" comparison isn't a supported capability.

**Decision: KEPT — no edit.** A well-reasoned KEEP: the complexity genuinely escalates within the
lesson's own established boundary, and every alternative job either belongs to a later lesson or isn't
gradeable by the existing widget.

## rns-02-03 — The Real Number Line Has No Gaps

Flagged: `k2`, `ch1`.
- Both collide with `k1` on "#² = # and #² = #. So √# is between:". `k1`→`k2` narrows the *same* running
  example (√2) from a tenths bracket (1.4–1.5) to a hundredths bracket (1.41–1.42) — `k2`'s own body

**Decision: KEPT — no edit** (both `k2` and `ch1`).

## rns-03-01 — Estimating Square Roots Between Integers

Flagged: `ch1`.
- `ch1` collides with `k1`: both "Between which two whole numbers does √# lie? Type the smaller one."
  Unlike `k2` (explicitly the LARGER bound — a genuine complementary direction) and `k3` (a different
  action, "closer to"), `ch1` added no distinguishing angle beyond a bigger radicand (150 vs 70) at the
  identical sub-task.

**Decision: REDESIGNED.** **Old job:** numeric entry of the smaller bracket bound (duplicate of `k1`).
**New job:** mcq judging which whole number √112 is actually closer to — a deliberately near-tied case
(distances 12 vs 9, not a lopsided gap like `k3`'s √95 case) chosen so it cannot be eyeballed and must be
computed. Re-verified independently: 10²=100 < 112 < 121=11², 112−100=12, 121−112=9, so 11 is closer
(confirmed by script, `Math.sqrt(112)=10.583`). Repointed the step's `variant` to the *existing* sibling
form `g8-rns-root-estimate`/`rnsCloserInteger` (already used by `k3` for the same "closer to" job family)
instead of touching the shared generator file — independently confirmed via `variantForStep` that it
resolves to a matching `mcq` surface and produces 12 distinct outputs across 12 seeds.

## rns-03-02 — Locating Irrationals on the Number Line

Flagged: `i2`, `ch1`.
- Both collide with `k1` on "To # decimal place, √# ≈ ____". `i2` (√2, rounds DOWN) sits immediately
  after `k1` (√10, rounds UP) — a deliberate both-directions pair, the same pattern found legitimate
  elsewhere in this packet. `k2` and `k3` already carry their own distinguishing angle ("a close call"
  precision-margin framing, and a two-decimal-place extension, respectively) and never collided. `ch1`
  (√83, rounds DOWN, one decimal place) added nothing new beyond a bigger number at the same precision
  and the same direction `i2` already covers — the genuine miss.

**Decision:** `i2` **KEPT** — no edit. `ch1` **REDESIGNED.** **Old job:** numeric compute-and-type
(duplicate direction/precision of `i2`). **New job:** mcq diagnosing which of four value+reasoning claims
about √83's one-decimal estimate is correct, adding a "compared at the wrong scale" misconception (the
wrong option reasons from the whole-number brackets 81/100 instead of the tenths brackets 82.81/84.64) —
not tested anywhere else in the lesson. Re-verified: 9.1²=82.81, 9.2²=84.64, 83−82.81=0.19 versus
84.64−83=1.64, so 9.1 is correct. Deleted the now-mismatched `numeric`-producing variant tag rather than
repoint it — no sibling form in `g8-rns-root-estimate` produces this reasoning-diagnosis mcq shape.
