## A. mult-div-fluency-g4 (9 lessons)

Contract: in each of these 9 lessons, `i1` and `i2` were byte-identical `columnCalc`/`areaModel`/
`estimateSlider`/`numberLineHop` widgets (same operands, same `commonResults`/`commonErrors`/
`commonLandings`, same feedback text) — only the `prompt` differed (generic "build the model" vs.
"classmate claims X" framing over the *same* task). Fix: `i2` now uses a genuinely different problem
instance (new operands), with every partial product / carry / quotient / remainder / landing and every
feedback string recomputed by hand for the new numbers. `i1` was left unchanged in all 9 lessons (kept
as the exploratory build/predict step, per the contract).

| Lesson | Widget | i1 (unchanged) | i2 (new) | Correct answer (i2) |
|---|---|---|---|---|
| g4m-01-03 | columnCalc | 1342 × 3 | 2153 × 4 | 8612 |
| g4m-01-04 | columnCalc | 487 × 6 | 356 × 7 | 2492 |
| g4m-01-05 | areaModel | 23 × 14 | 27 × 16 | 432 |

For the two `columnCalc` lessons (g4m-01-03, g4m-01-04), the new `commonResults` distractor values were
generated by simulating the carry chain digit-by-digit in Python (drop a specific carry, recompute the
resulting written digits) rather than guessed, so every "stranded the carry" / "X short" feedback
string is a literally true description of that exact wrong value:

- g4m-01-03: 2153×4=8612. Dropping the tens→hundreds carry gives 8412 (delta 200). Dropping the
  ones→tens carry gives 8602 (delta 10).
- g4m-01-04: 356×7=2492. Dropping the ones→tens carry gives 2452 (delta 40). Dropping both carries
  gives 2152 (delta 340; the generic "two carries went missing" text was already number-free and true).

For the `areaModel` lessons, the four partial-product regions were recomputed and written into
`successFeedback` (e.g. g4m-01-05: 27×16=432 = 200+120+70+42). For the `estimateSlider` lessons, the
`target` is the friendly/compatible-number estimate (not the exact quotient) matching the existing
in-course convention (e.g. g4m-03-01 target 700, exact 687); `min`/`max`/`ticks` were left unchanged
since they are a generic broad-range slider scale, not tied to the specific dividend. For the
`numberLineHop` lessons, `commonLandings` overshoot/undershoot values and their remainder deltas were
recomputed for the new hop/hops/dividend.

### g4m-03-01 slug rename

`g4m-03-01`'s slug `"four-digit-by-one-digit"` was byte-identical to multiplication lesson
`g4m-01-03`'s slug. Renamed to `"four-digit-division-by-one-digit"` (the contract's suggested value).

**Slug-usage investigation (why this is safe):** grepped `src/` for every `.slug` reference before
touching anything. `Lesson.slug` is a required schema field (`src/lib/schema.ts`) but is never read for
routing — lesson pages are addressed by `lessonId` (e.g. `/learn/[lessonId]`), and every `/courses/...`
URL keys off `Course.slug`, a completely separate field, not any individual lesson's slug. The only
runtime consumer of lesson-level `slug` found is `scripts/gen-manifest.mjs`, which copies it verbatim
into `content/curriculum-manifest.json` as a display field (no uniqueness check, no URL construction).
One test, `src/lib/session244.multFluencyIdentity.test.ts`, asserts `lesson.slug === identity.slug`,
but only for the unrelated `multiplication-division` course's fixed six lessons — it does not touch
`mult-div-fluency-g4`. No test or route in the repo enforces or depends on mult-div-fluency-g4 lesson
slugs being any particular value or being globally unique (only this one accidental collision existed,
confirmed via `grep -h '"slug"' content/courses/*/lessons/*.json | sort | uniq -c`, which showed exactly
one duplicate pair before this fix and zero after). **Residual impact:** `content/curriculum-manifest.json`
is a generated, checked-in file and will still show the old slug value for `g4m-03-01` until
`scripts/gen-manifest.mjs` is next run — that regeneration was out of scope for this packet (no
npm/build scripts were run per the task rules) and does not affect any code path today.
